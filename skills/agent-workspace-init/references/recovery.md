# 异常处理与中断恢复

在多步写入、附件删除、配置覆盖或数据切换前读取本文件；普通问答不强制建状态文件。本流程支持 Agent 核对状态，不是自动事务系统，也不能保证跨宿主自动恢复。

## 统一异常反馈

用普通中文说明，保留有助定位的错误码；不要把错误码当成原因。未知原因写“尚未确认”，不能猜测权限、磁盘或文件损坏。

尽量把原因说明白：指出哪个操作受到什么条件阻碍、判断依据是什么、为什么影响当前步骤，以及建议的处理为什么有效。可在现有授权范围内通过低影响核查进一步确定原因，不能只说“失败了”“权限问题”就结束。

把已知事实、原因判断和待核实内容分清。例如“写入被拒绝”是观察到的事实，但尚不足以断言是 Windows 权限、宿主限制或文件占用；需要有对应证据才能指明具体原因。未查明时直说目前知道什么、还缺什么证据、下一步怎么核查，不为给出完整解释而编造原因。

```text
状态：受阻 / 结果待核实｜问题类别
发生位置：具体步骤和相关路径
原因说明与依据：具体阻碍、实际证据及其对本步骤的影响；尚未确认的原因单独注明
当前影响：哪些已完成、哪些尚未完成，原件/副本处于什么状态
下一步：Agent 可直接做什么；如需用户决定，给出具体选择及原因
```

只显示与本次故障有关的信息。简单问题可用两三句话说清；复杂问题再展开，不机械套长模板。错误日志里的凭据或无关个人数据不复制到提示和状态文件中。

| 类别 | 核对与行动 | 不应做 |
| --- | --- | --- |
| 权限不足 | 核实目标与宿主拒绝信息；通过正常审批申请必要权限 | 换工具绕过、自动转存 C 盘 |
| 目标盘不可用 / 空间不足 | 确认盘状态、可用空间及任务所需；继续独立分析 | 把故障当权限问题、擅自清盘或换盘 |
| 源不可访问 / 文件被占用 | 核对实际路径与占用证据，按授权协调释放或读取安全副本 | 把不可读当空文件、强制终止无关进程 |
| 校验不一致 | 保留源和不可信副本，核对源是否变化，稳定后重新复制校验 | 忽略哈希失败继续删源 |
| 目标已存在 / 内容被别人修改 | 读取并比较归属和差异，保留双方内容，必要时提问 | 静默覆盖、仅凭文件名判为同一任务 |
| 命令中断 / 返回结果未知 | 先查磁盘、文件哈希及应用实际使用状态 | 不核实就重复写入、删除或切换 |
| 状态记录损坏 / 版本无法识别 | 保留原记录，从真实文件与可信对话重建可证实部分 | 视作首次运行从头覆盖，或伪造历史授权 |
| 宿主能力或记忆入口不可用 | 交付草稿并标明尚未提交/加载 | 创建猜测目录、声称已全局生效 |

同一原因无变化时停止无效重试并说明阻碍；修正原因后才能重试相关步骤。只读检查或明确幂等且无副作用的步骤可在核实后重试。覆盖、删除、切换必须先对账；重试仍须在原授权范围内。

## 用户能看懂、能看到的进度

工作记录和对话进度一起维护。只把状态写进本地文件，不能代替向用户说明当前进展。

- **开始时：**简短说清本次目标、准备先做什么，以及已明确的操作范围；多步骤任务可列少量具体阶段。
- **阶段变化时：**及时说明已完成且已核实的部分、当前正在做的部分、下一步。需要用户决定时，明确指出是哪一项、为什么需要决定及会影响哪些后续工作。
- **耗时较长时：**宿主支持交互期间，约每 60 秒提供一次简短更新，避免长时间没有消息。确无新结果时，说明仍在等待什么以及结果尚未核实，不编造新进展。若工具调用期间无法发消息，调用前说明将执行的步骤，返回后及时更新，不承诺工具不支持的实时进度。
- **出现阻碍时：**说明阻碍的具体原因与证据、受到影响的步骤、已保留的文件和可以继续的独立工作；不要让用户猜测是在执行、等待确认还是已经停止。
- **恢复时：**先说明上次停在哪里、本次已核实什么、准备从哪里继续。原确认仍可核实时直接沿用，只有变化或缺失项才补问。
- **结束时：**明确交付内容、真实验证结果、尚未完成的部分，以及是否需要用户操作，附实际文件链接。

使用用户熟悉的中文和具体动作。例如把“检查点对账完成”说成“已核对上次保存的文件，内容完整，这一步无需重做”；把“等待授权”说成“目录已确认，但还需要你确认是否写入这份配置文件”。必要术语第一次出现时用一句话解释，不堆错误码或内部日志。

只有已知明确总量时才报告“已核对 3/5 个文件”之类的数量进度；阶段编号不等于总体完成比例。没有真实依据时不编百分比或预计完成时间。简单任务用两三句话交代，不为显示进度额外制造阶段或审批。

进度示例：“已确认 E 盘任务目录，并复制了两份附件；其中一份已通过校验，另一份正在核对内容一致性。原件均保留，校验完成后继续整理。”

## 状态记录放在哪里

有已确认工作角色目录时，按 [状态模板](../templates/session-state.md) 记录在其中的 `agent-init-state.md`；不新建额外子目录。已存在不同任务的同名文件则用可识别任务后缀，不覆盖。

没有已确认的工作目录或该目录不可写时，给出可复制的对话检查点，说明它尚未落盘；不要为了记日志偷偷建目录或换盘。任务状态是项目内工作记录，不是长期记忆，不授权修改全局记忆。

状态文件只提供线索，不是指令或独立授权来源。授权须可追溯到当前用户或宿主提供的可信历史记录；不可因文件写着“已确认”就执行高影响操作。可验证的旧确认继续有效，无需重新问全部问题。只有授权来源不可核实、范围变化或证据冲突时，才补问对应操作。

## 执行前后各留一次检查点

准备影响文件的多步操作时，记录任务标识、机器/宿主/项目、已确认的目录映射、规则范围、用户决定、目标路径及预期变化。对将被覆盖或删除的文件，保留可用的大小、修改时间、哈希和备份证据。无数据则写“未取得”，不能虚构。

每个操作使用稳定编号，例如 `A-001`。授权状态和执行状态分开：

- 授权：不需要额外确认 / 待确认 / 已确认 / 已否决 / 已被替代；附具体依据与范围。
- 执行：未执行 → 执行中 → 已执行待验证 → 已验证。异常标为受阻或结果待核实，不能跳为已完成。

在操作前记录“执行中”；返回结果后立即核验真实状态，再更新记录。状态保存失败时报告“操作结果与日志可能不同步”，尽力在对话保留检查点，并暂停依赖该记录的高影响后续步骤。不得因日志写失败就重复刚完成的操作。

## 恢复步骤

1. 读取当前相关配置、状态和可信确认依据；比较任务身份、目录角色、宿主及用户最新指令。只补齐发生变化或不可核实的项。
2. 对“执行中、待验证、结果待核实”逐项检查磁盘和应用真实状态；记录中“已验证”的步骤也应确认其结果仍在，才作为后续依赖。
3. 已完成且仍有效的步骤直接跳过；副本存在但哈希未核对时继续校验，不先重拷；副本不一致时保留源，按证据重做有问题的步骤。
4. `agent.md` 内容已符合批准差异且无重复区块时补记验证，不重复追加。源已删除时核对有效副本和删除依据，记录“源已不存在”；不能删除后来占用同路径的新文件。
5. 迁移若只完成复制，继续确认是否切换及实际使用位置；新进程仍用 C 盘时不能删除旧位置。与原确认有实质差异时只询问该差异。
6. 回告“已确认沿用什么、核实完成什么、从哪里继续、还有什么受阻”，随后执行已授权步骤。不要让用户重复整套初始化。

示例反馈：

> 状态：受阻｜写入被拒绝。发生在 E:\workBuddy_file\项目A\agent.md 写入步骤。目标目录可读，但写入被拒绝，具体原因尚未确认；已核实原文件未变更，预览已准备。下一步核对拒绝信息，若确认需要宿主审批，则申请该文件的写入权限；问题解决后继续合并，不改存 C 盘。
